# 코어는 UI 프레임워크를 모른다 — 단, Streamlit 화면은 교체하지 않는다

졸업 프로젝트 전시회 시연을 앞두고 "Streamlit 의존성을 없앤 배포 가능한
프로그램"을 목표로 검토했으나, 실측 결과 Streamlit 자체가 병목이 아니었다.
그래서 **화면은 Streamlit으로 유지하고, 탐색·예측·설명 코어에서만 UI
프레임워크 결합을 제거**한다. 코어는 `core/` facade로 공개 표면을 명시하고,
진행률 같은 UI가 필요한 기능은 코어가 옵셔널 콜백(`on_batch(done, total)`)을
노출하고 화면이 선택적으로 소비한다. 코어는 숫자만 말하고 표현은 화면이
정한다.

## 근거가 된 측정 (CPU, torch 2.12.0+cpu, GPU 없음)

| 항목 | 실측 |
|---|---|
| 모델 로드 | 3.7초 |
| 첫 추론 (워밍업) | 9.1초 |
| 워밍업 이후 추론 1개 | 0.44초 |
| 워밍업 이후 배치 8개 | 0.83초 |

병목은 모델 크기가 아니라 **첫 추론 9.1초**와 **SHAP 약 30초**
(64샘플 × 배경 4개 = 추론 256회) 두 곳이었다. 추론 자체는 사이트당 약 0.1초로
시연에 충분하다. 프레임워크 교체는 이 두 숫자를 개선하지 않는다.

## 고려한 대안

- **FastAPI로 전면 전환하고 Streamlit을 버린다**: 기각. 화면 842줄
  (`app.py` 490 + `xai/view.py` 352)을 3주 안에 다시 쓰는 위험을 전시회가
  걸린 일정에 둘 수 없고, 되돌아갈 경로가 없어진다. 더 결정적으로, 원래
  FastAPI가 필요하다고 본 이유(SHAP 진행률 표시)가 Streamlit에서도 구현
  가능했다 — `shap.KernelExplainer`에 넘기는 콜백 안이 아니라 `_logits`의
  배치 루프에 훅을 넣으면 32단계 진행률이 나온다.
- **Streamlit 결합을 그대로 둔다**: 기각. `predict.py`가 모듈 최상단에서
  `streamlit`을 import해 코어를 화면 없이 테스트할 수 없었다. 가중치 없이
  돌아가는 테스트를 만드는 것이 이 작업의 주된 가치다.
- **코어 파일을 `core/` 패키지로 물리적으로 옮긴다**: 기각. `app.py`의 import
  경로가 바뀌어 팀원이 작성한 화면 파일을 건드려야 한다. 파일은 제자리에
  두고 facade만 추가한다.

## 결과

- Streamlit 화면과 (장래의) HTTP API가 **같은 코어 위에 동시에** 붙을 수
  있다. 경계가 실제로 그어졌다는 증거는 이 공존 상태 자체다.
- `@st.cache_resource`를 떼는 대신 실제로 캐싱되는 대체물이 있어야 한다.
  Streamlit은 상호작용마다 스크립트를 재실행하므로, 캐시가 없으면 모델을
  매번 다시 로드한다. 모듈 수준 싱글턴은 `sys.modules`가 재실행 간 유지되기
  때문에 유효하다. 워밍업도 같은 이유로 import 부작용이 아니라
  `load_predictors()` 안에 둔다.
- 사전계산 SHAP 캐시의 키는 기존 `@st.cache_data`의 키와 같아야 한다
  (`model_key, head, window_seq, nsamples, n_background`). 서열만으로 키를
  잡으면 사용자가 샘플 수를 바꿨는데도 다른 설정의 값을 돌려주게 된다.
  설명을 보여주는 도구가 설정을 무시하면 모든 숫자의 신뢰가 흔들린다.
- FastAPI 층을 추가할지는 팀원과 상의 후 별도로 결정한다. 이 ADR은 그것을
  배제하지 않고, 가능하게 만들어 두는 데까지만 결정한다.
