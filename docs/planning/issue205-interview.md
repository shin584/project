## 확정된 결정

사용자는 첫 라운드 Q1~Q4에 대해 "추천대로 진행해"라고 답했다.

### Q1 — 실행 묶음과 원시 자료

측정 전에 실행 ID·계약·관련 코드·모델·설정을 고정한다. reference·본검증·진단·
staging 결과와 원시 자료의 checksum을 연결하며 서로 다른 실행을 섞지 않는다.
기존 #193 자료를 보존하고 #205 결과를 별도 묶음으로 남긴다. 원시 자료는
재생성 가능한 임시 파일만으로 대신하지 않고 보관한다.

[ADR 0002](../adr/0002-preserve-runtime-verification-provenance.md)에 근거 보존
결정을 기록했다. 보관 위치는 Q9에서 확정했으며 실제 복구 가능 여부는
#205 구현 후 새로운 실행 묶음에서 검증한다.

### Q2 — 독립 오프라인 복구

준비된 코드·모델·manifest·필수 의존성 사본을 독립 위치로 복구해 최소 실행한다.
기존 Python 실행 파일·표준 라이브러리·OS 구성은 명시적인 외부 전제로 허용한다.
실행 중 원본 작업 폴더와 원본 모델 경로 접근을 차단해 우발적 fallback을 검출한다.
새 환경 설치와 최종 배포 검증, OS 수준 네트워크 차단은 #204에 둔다.
이번 실행에서 사용하는 네트워크 차단 방법과 그 한계를 기록한다.

### Q3 — SHAP 공유 잠금

공용 SHAP 함수에서 NumPy 전역 RNG 상태 저장부터 seed 설정·계산·복원까지
공유 잠금으로 보호한다. 같은 잠금을 사용하는 SHAP 호출끼리의 재현성을
보장하며 다른 전역 RNG 소비자까지 보호한다고 주장하지 않는다.
별도 프로세스 격리를 도입하는 대신 기존 호출 구조를 유지한다.
정상 완료와 seed 설정 이후의 예외·협력적 취소에서도 복원을 검증한다.
강제 프로세스 종료를 살아 있는 호출자의 RNG 복원과 같은 보장으로 취급하지 않는다.

### Q4 — 차분 실패의 진단과 종료 조건

사례·점·방향·step sweep·허용 오차를 먼저 등록하고 실패 위치마다 조사한다.
입증된 원인과 미해결 사례를 구분해 기록할 수 있다. 기존 실패와 그 종합 판정은
유지한다. 두 autograd가 일치한다는 사실만으로 모든 실패를 ReLU 꺾임 탓으로
단정하지 않는다.

## 두 번째 라운드의 배경

사용자가 SHAP 샘플수 및 IG 단계수 증가와 Cas12a gradient 검사 조건 완화를
제안했다. 이후 Q5·Q6 추천안을 승인했으며, 기존 기본값과 기준을 보존하고
정밀 설정을 후보로 검증하는 방향을 확정했다.

현재 동결 계약은 사용자 설정 32/64/4와 비교 실행 IG 256·SHAP 512/32를 구분한다.
기존 IG 256 결과는 고정된 사례·선택 헤드·기존 경로에 한정되며, SHAP 512/32는
안정성이 입증된 정답으로 취급하지 않는다. Cas12a의 기존 이중 입력 gradient와
#195에서 결정할 합성 경로의 gradient는 검증 대상을 구분해야 한다.

논의가 끝날 때 새 검증 계획, 사용자 설정 변경 여부, 후속 담당 티켓을 명시한다.
기존 `docs/runtime/contract.json`과 측정 자료는 이 인터뷰에서 변경하지 않는다.

## 추가 질문을 위한 사실 확인

아래 값은 기존 `.packaging/issue193/verification-core.json` 및 `diagnose.json`을
읽어 확인한 역사적 측정값이다. 이번 인터뷰에서 재측정하거나 #205의 새 실행
근거로 승인한 값이 아니다.

- IG 완결성: 32단계에서 SpCas9 2/4, Cas12a 1/4 통과, 합계 3/8 통과·5/8 실패.
  256단계에서는 각 4/4로 총 8/8 통과. 다른 입력·헤드·경로로 일반화하지 않는다.
- Cas12a 좌표 gradient 검사: C3(34개 A), 원입력 `x`, `Input_Seq`의 상대 L2 오차
  `0.02225866089087975`가 기준 `0.02`를 초과했다. 같은 지점 cosine은
  `0.9997548535561704`로 기준 `0.999`를 통과했다. Cas12a의 나머지 15개
  사례×점×입력 조합은 두 항목 모두 통과했다.
- Cas12a C3 방향 차분의 최대 상대오차도 `0.12246829313722153`로 기준 `0.1`을
  초과했다. 중앙값 `0.0016049126469110122`의 통과가 최대값 실패를 없애지 않는다.
- SHAP 512/32는 seed 0의 비교 실행이며 그 설정의 seed 간 안정성은 미검증이다.
  현 코드의 지배적인 모델 입력 평가량은 샘플수×배경수에 비례하므로 64/4에서
  512/32로 바꾸면 약 64배다. 실제 실행시간이나 RAM이 같은 비율이라는 뜻은 아니다.

공식 문서가 뒷받침하는 해석:

- [Captum IG 문서](https://captum.ai/docs/extension/integrated_gradients)는
  단계수를 정확도와 속도의 절충으로 설명한다. 단계수 증가는 적분 오차 개선을
  위한 합리적인 실험이지만 gradient 자체의 정확성을 대신 검증하지 않는다.
- [SHAP KernelExplainer 문서](https://shap.readthedocs.io/en/latest/generated/shap.KernelExplainer.html)는
  샘플수 증가가 추정 분산을 줄인다고 설명한다. 현재 코드는 배경 생성과 부분집합
  샘플링에 같은 seed를 사용하므로 두 변동을 분리한 실험이 필요하다.
- [PyTorch gradcheck 문서](https://docs.pytorch.org/docs/stable/generated/torch.autograd.gradcheck.gradcheck.html)는
  기본 허용 오차가 double 정밀도를 전제하고 float 입력과 비미분점에서 검사가
  실패할 수 있음을 설명한다. 이것만으로 현 실패 원인이 입증되거나 새로운
  완화 기준이 정당화되는 것은 아니다.

## 두 번째 라운드 — 확정된 결정

사용자는 Q5·Q6에 대해서도 "추천대로 진행해"라고 답하고, 증가한 계산량의
시간과 리소스 비용을 질문했다.

### Q5 — 증가한 계산량의 적용

기본 32/64/4를 유지하고, IG 256과 더 큰 SHAP 설정은 정밀 재시도 후보로
검증한다. SHAP은 배경 고정 샘플수 변화와 샘플수 고정 배경 변화를 분리해
단계적으로 실험하고 실행시간도 측정한다. #205의 검증 결함 보수 뒤 신뢰할 수
있는 harness로 검증하며, 실제 사용자 재시도 제공과 설정 품질 검증은
#199/#200/#201의 계열별 범위와 연결한다. 기본값 변경을 원한다면 별도 범위
결정과 사전 등록이 필요하다.

### Q6 — Cas12a gradient 판정 기준

기존 2% 기준과 원래 실패를 보존하고, 동일한 점·방향의 step sweep 및
kink 교차 진단으로 차분 오차와 gradient 구현 문제를 구분한다. 새로운 검사법이나
허용 오차가 필요하다는 근거가 확보되면 별도 버전의 계약을 사전 등록해 새 실행에
적용한다. 기존 실패를 새 기준으로 소급해 통과로 바꾸지 않는다.

## 계산 비용 조사

기존 raw에는 설정별 IG·SHAP 계산시간과 RAM 비교가 없다. `ram.json`의
SpCas9 10.1초·Cas12a 13.4초는 모델별 새 프로세스에서 시작·import·적재·전방·
IG 32 전체를 합친 시간이다. Cas12a에는 TensorFlow import 영향도 포함돼 있다.
이 값을 IG 단독 시간 또는 256단계 비용의 기준값으로 사용하지 않는다.

구현에서 확인한 계산 구조:

- IG는 청크 8을 유지할 때 32단계의 적분 청크 4회가 256단계에서는 32회가 된다.
  적분 작업은 8배지만 끝점 평가 같은 고정 비용이 있어 전체 시간이 정확히
  8배라는 뜻은 아니다. 주요 gradient 계산 그래프의 배치 크기는 8로 유지된다.
- SHAP의 지배적인 서열 평가량은 샘플수×배경수다. 64/4에서 512/4는 약 8배,
  512/32는 약 64배다. 모델의 전방 배치는 최대 64행으로 유지하지만 모델에 넣기
  전에 전체 합성 서열과 Cas12a 파생 특징을 만들므로 호스트 버퍼는 증가한다.
- Cas12a에서 샘플×배경 전부를 한 번에 합성한다고 계산한 one-hot 버퍼는
  64/4 약 0.133 MiB에서 512/32 약 8.5 MiB, 354개 float32 특징 행렬은
  약 0.346 MiB에서 약 22.125 MiB가 된다. 임시 복사·모델 활성값·라이브러리
  메모리를 제외한 배열 크기이며 프로세스 전체 RAM 예측값이 아니다.

개발 PC에서 두 non-NT 모델의 대표 사례 S1·C1과 선택 헤드에 대해 제한된
성능 측정을 수행했다. [성능 측정 기록](../runtime/issue205-performance.md)에
명령·원시 자료·시간·CPU·RSS·180초 제한으로 인한 부분 중단을 기록했다.
주요 설정 5개는 두 모델 모두 각 3회 완료했으며, 성능 호출 전체는 52회 완료했다.
제품 코드·동결 계약·checkpoint는 변경하지 않았다. 수치 품질 게이트 재검증과
구분한 탐색적 성능 자료이며 NT 및 UI 전체 트리 비용으로 일반화하지 않는다.

## 세 번째 라운드 — 확정된 결정

### Q7 — non-NT 정밀 재시도의 대기시간 예산

사용자는 Q7 추천안에 "그렇게해"라고 답했다. 선택한 예측 행 한 건의 non-NT
정밀 재시도는 약 1분까지 기다릴 수 있는 후보를 검토하되, 예상 비용·진행률·취소를
제공한다. 이는 허용 가능한 대기시간의 설계 목표이며 모든 입력이 1분 안에
끝난다는 보장이나 강제 timeout 구현 결정이 아니다.
설정의 품질 승인은 별도 검증이 필요하며 NT의 예산은 별도 성능 측정 후 논의한다.

### Q8 — 중단된 검증의 재실행

측정 실행이 중단되거나 관련 코드·계약·모델·설정이 달라지면 새로운 실행
묶음을 만들고 필수 측정을 처음부터 재실행한다. 이전의 완료 단계는 진단 자료로
보존하며 새 실행의 증거로 재사용하지 않는다. 완료된 동일 묶음의 원시 자료로
요약을 다시 조립하는 것은 허용한다. 단계별 측정을 재사용하는 재개 기능은
이번 #205에서 추가하지 않는다. 수치 기준 실패를 정상적으로 기록한 단계는
실행 중단과 구분하며, 다른 필수 단계도 수행해 실패 목록을 완성한다.

### Q9 — 검증 원시 자료의 보관 위치

기존 백업 체계 아래 `C:/project-backups/dashboard-v3/issue205/<run_id>/`에
고정 계약·관련 코드 스냅샷·모델 manifest·원시 결과를 보관하고,

두 로컬 볼륨의 사본을 외부 백업이나 물리적으로 독립된 보관이라고 주장하지 않는다.
이 경로는 #192의 실제 보관 구조를 따른다. 새로운 수치 검증 묶음은 아직
생성하지 않았으며 이번 인터뷰에서는 이 경로에 복사를 수행하지 않았다.

유일한 개선책으로 확정하거나, 기본값을 올리거나, 새로운 설명 기법의 연구 범위를
추가하는 지시로 해석하지 않는다. 합의한 계산량 안에서 품질을 입증하지 못하면
해당 실패·미검증 상태를 보존하고 후속 화면에서 경고·진단·재시도로 다룬다.

## 기존 NT에서는 문제가 없었는가 — 사실 확인

사용자는 이전에는 문제가 없었던 것 같으며 모델 구조 차이가 원인인지 질문했다.
이 질문 시점에는 Q8·Q9 답변이 없었고 이후 별도 메시지에서 승인됐다.
이 질문을 NT/non-NT 비교 연구의 추가 지시로 해석하지 않는다.
모델을 새로 실행하지 않고 보존된 코드·자료를 확인했다.

- 기존 [NT baseline](../equivalence-baseline/capture.json)에도 IG 32단계 완결성
  오차 SpCas9 `1.1668063658998293`, Cas12a `0.30689201787177944`가 기록돼 있다.
  같은 서열의 IG 예측값과 SHAP 예측값도 다르다. 단위·함수·설명 경로가 달라
  현재 non-NT 오차와 직접 크기를 비교하거나 원인을 확정하지 않는다.
- 기존 [gate2 범위 설명](../gate2/README.md)은 IG pred/완결성 문제의 계산식을
  이 전환 작업에서 바꾸지 않으며, 기존 결과와의 동등성이 과학적 타당성 검증을
  뜻하지 않는다고 명시한다. 오차를 기술적 참고에 표시하며 그래프를 출력하는
  기존 동작은 동결한 품질 기준의 통과와 다르다.
- 기존 [시연 기록](../demo-sequences.md)에도 SHAP 64샘플 특이행렬 경고와
  재계산 시 값·순위 변동 가능성, 낮은 가법성 오차가 안정성을 보증하지 않는다는
  설명이 있다. 동일 사전계산 캐시를 읽어 화면 간 결과가 일치하는 검사는
  새로운 계산의 seed 간 안정성 검사를 대신하지 않는다.
- NT IG는 토큰 임베딩을 보간한 뒤 염기 위치에 투영한다. non-NT IG는 원핫을,
  Cas12a의 현 이중 입력 경로는 원핫과 354개 파생 특징을 각각 보간한다.
  동일한 32단계라도 같은 함수·경로의 검사가 아니다.
- 기존 NT SHAP도 염기 위치 30/34개를 마스킹하는 공용 KernelSHAP 루프를 쓴다.
  NT의 토큰 수가 적으므로 64샘플이 충분했다는 설명은 성립하지 않는다.
- 구조·학습 가중치·설명 경로가 수렴 난도에 영향을 줄 가능성은 있지만,
  동일 계약·단위·전체 사례를 적용한 통제 비교가 없다. 현재 gradient 차분의
  실패에는 float32·차분 간격·비미분 경계의 영향도 조사해야 한다. 구조만으로
  원인을 단정하지 않으며, 이번 검증에서 더 넓은 사례와 수치 기준을 적용한
  효과를 함께 구분한다. #205의 RNG·캐시 식별·종합 판정 결함은 구조와 별개다.

### Q13 — 조건부 float64 진단의 허용 범위

승인된 float32 진단 후에도 원인이 남은 위치에만 float64 진단을 한 차례
허용한다. 입력만 double로 바꾸지 않고, dtype 외 구조·연산 설정·헤드·가중치 값을
대조한 별도 진단 사본을 사용한다. 기존 runtime은 float32를 강제하므로 이를
그대로 고정밀 경로라고 부를 수 없다. 실제 두 checkpoint의 float64 전방/역방향
실행 가능성은 아직 확인하지 않았다.

원본 모델과 배포 runtime은 바꾸지 않는다. 사본 적격성을 확인할 수 없거나 연산이
지원되지 않으면 `고정밀 진단 불가`, 실행 후에도 원인이 남으면 `원인 미해결`로
종료한다. 수동 LSTM·backward 재구현으로 확대하지 않는다. float64에서도 비미분
경계는 남으며, 계산 정밀도 개선을 기존 float32 실패의 통과 전환으로 사용하지 않는다.

현 코드·공식 문서 근거:

- `non_nt_runtime.py`의 forward/gradient가 float32를 강제하고 `.keras` 내부
  Input·층·Cas12a 내부 양방향 LSTM의 dtype도 float32로 명시돼 있다.
- [Keras layer 문서](https://keras.io/api/layers/base_layer/)와
  [dtype policy 문서](https://keras.io/api/mixed_precision/policy/)에 따라
  층 자체의 compute/variable dtype을 확인해야 한다.
- [clone_model 문서](https://keras.io/api/models/model_saving_apis/model_config_serialization/)의
  clone은 새 가중치를 만들므로 원 가중치의 명시적 복원과 적격성 검사가 필요하다.
- float64 배열은 같은 원소 수에서 float32의 2배 bytes이나 전체 RSS·계산시간이
  2배라는 뜻은 아니다. 관련 시간·RAM은 아직 실측하지 않았다.

대상별 시간 예산·차분 간격·비교 지표·종료 처리는 Q16에서 확정했다.

### Q14 — SHAP 후보 선정과 제한된 검증의 통과 규칙

모델별 4사례 모두에서 실제 측정한 축에 기준 위반이 없는 설정만 1차 후보로
둔다. 미측정 축은 미검증이며 통과로 간주하지 않는다. 1차 fresh 호출 전체의
관측 wall time 최댓값이 가장 짧은 설정 하나를 임시 선정한다. 동률이면
샘플수×배경수가 작은 순으로, 여전히 같으면 샘플수·배경수 순으로 정한다.

독립 seed 3×3 확인에서는 모델별 4사례 모두 다음을 충족해야 제한된 조건의
seed 안정성 확인 후보로 인계한다.

- 모든 필수 값이 유한하고, 모든 실행의 가법성 오차가 SpCas9 `5e-3`, Cas12a
  `1e-3` 이내다.
- 9개 조합의 모든 36쌍에서 상관 `>=0.9`, 최대 절대차
  `<=0.25*max|phi(배경0,부분집합0)|`다.
- `(0,0)` fresh 재호출의 최대 기여도 차가 `<=1e-9`다.

이는 기존 숫자를 새 독립 seed 범위에 사전 적용하는 추가 규칙이다. 필요한 측정이
누락되거나 상관을 계산할 수 없으면 통과시키지 않는다. 후보가 실패하면 다른
후보를 자동으로 계속 시험하지 않는다. 512/32를 정답으로 삼는 새 승인 조건은
추가하지 않으며 기존 기본 설정 대 정밀 비교의 판정은 그대로 보존한다.

### Q15 — IG 후보의 선정과 표현

모델별 4사례 모두 필수 값이 유한하고 완결성 기준(SpCas9 `5e-3`, Cas12a
`1e-3`)을 충족하는 설정 중, 관측 wall time 최댓값이 가장 짧은 설정을
`완결성 개선 후보`로 인계한다. 동률이면 단계수가 작은 설정을 고른다.
32/64/128과 256의 위치별 상관·scaled 차이·강한 위치의 부호 일치는 기존
해상도 기준을 적용해 별도 보고한다. 256과 자기 자신을 비교해 해상도 통과로
계산하지 않으며 기존 gradient 실패도 유지한다.

256은 승인된 최대 시험 단계이며 정답이 아니다. 이번 선정은 완결성 개선의
제한된 근거로 남기고 최종 설정 품질 승인은 #199/#200에 둔다. 추가 512단계
실험을 자동으로 포함하지 않는다.

### Q16 — float64 진단의 간격·비교 기준·시간 한도

float32의 6개 h에 `1e-5,1e-6`만 추가한 8개를 사전 고정한다.
좌표 cosine/상대 L2, 방향 median/max와 원시 gradient·차분·잔차를 기록하며
비교선은 기존 `0.999/0.02`, 방향 `0.02/0.1`을 유지한다. 연속한 두 h의
일치 여부, 같은 h에서의 float32 대비 잔차 변화, 경계 교차 증거를 함께 보고한다.
결과를 본 뒤 h를 추가하거나 기존 float32 실패를 통과로 바꾸지 않는다.

고정밀 추가 작업 예산은 총 30분이다. 모델별 순차 실행하며 사본 적격성
확인에 최대 5분, 진단에 최대 10분을 둔다. 이는 실측 시간 예측이 아닌 허용 예산이다.
예산 소진을 사전 등록된 조건부 진단의 종료 조건으로 허용하고 `time_limited`와
완료·미완료 대상 수를 기록한다. 적격성 실패는 `unavailable`, 실행 완료 후에도
원인 불명은 `unresolved`로 구분한다. 비정상적인 필수 파이프라인 중단·조건 변경은
Q8의 새 실행 묶음 규칙을 그대로 따른다.

정밀도 영향 지지·경계 교차 증거·혼합 가능·미해결을 증거 수준으로 기록하며
float64의 개선만으로 원인을 단독 확정하지 않는다.

## 여덟 번째 라운드 — 확정된 결정

사용자는 추가 라운드에서 Q17 추천안에 "그렇게해"라고 답했다. Q1~Q16은 유지한다.

### Q17 — 추가 조사 상태의 종합 판정과 종료코드

필수 검증 결과와 추가 조사 상태를 별도로 기록하고 아래 우선순위로 종합한다.

| 상황 | 종합 판정 | 종료코드 |
| --- | --- | --- |
| 필수 검증 실패·누락 또는 근거 불일치 | `fail` | 0 이외 |
| 필수 검증 통과, 추가 실험 일부 미검증 또는 고정밀 진단 `unavailable/time_limited` | `incomplete` | 0 이외 |
| 필요한 조사 완료, 원인만 `unresolved`이거나 적합한 후보 없음 | `completed_with_findings` | 필수 검증이 모두 통과했다면 0 |
| 필수 검증·해당 추가 조사 모두 완료하고 기준 충족 | `pass` | 0 |

필수 실패는 다른 상태보다 우선하며, 원래 수치 실패를 원인 진단이나 후보 결과로
통과로 바꾸지 않는다. 종료코드 0도 전체 헤드·경로의 품질 승인을 뜻하지 않는다.
`unavailable`은 적격성 조사를 마쳤더라도 고정밀 근거를 확보하지 못한 상태다.
`unresolved`는 계획한 측정을 마쳤으나 원인이 남은 상태이며, 측정 누락과 구분한다.
조건상 필요하지 않은 float64 진단은 미검증 항목으로 계산하지 않는다.

사전 등록된 예산 소진은 현재 묶음과 완료 결과를 보존하고 종료한다. 이 상태만으로
Q8의 전체 재실행을 요구하거나 부분 측정 재개를 허용하지 않는다. 예기치 않은
중단·조건 변경에는 기존 Q8의 새 묶음·필수 측정 전체 재실행 규칙을 적용한다.
