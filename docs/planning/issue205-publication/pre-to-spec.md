# #205 검증 결함 보수 구현 명세

상태: [설계 인터뷰](issue205-interview.md) Q1~Q13 승인 완료, 후보 선정·판정과
고정밀 진단의 세부 프로토콜은 후속 라운드 진행 중인 초안이다. 제품 결함 보수와
수치 품질 재검증은 아직 수행하지 않았다. 이 문서는
[#205](https://github.com/shin584/project/issues/205)의 요구사항과 승인된 결정을
구현에 인계하며, 티켓의 수용 기준을 대체하거나 축소하지 않는다.

## 목적과 유지 조건

필수 검사 누락·오프라인 실패·서로 다른 실행의 혼합이 통과로 기록되지 않도록
검증 도구를 보수하고, 두 실제 non-NT 모델을 다시 검증해 근거와 인계를 정정한다.

- 작업 기준은 `dashboard_v3`, `c7df95b22683fbcefc0e560266bff01ef6190dc2`.
  후속 작업은 이 브랜치 또는 여기서 파생한 티켓별 워크트리에서 수행한다.
  병행 변경을 통합한 경우 실제 검증 기준 커밋·관련 코드 hash를 다시 고정한다.
- Keras 3.14.1 + torch backend 채택과 원본 checkpoint를 유지한다.
  기존 데스크톱 프로그램·모델·#193 자료를 보존한다.
- 사용자 기본값 IG 32, SHAP 64샘플/배경 4개를 유지한다.
  동결된 [계약](../runtime/contract.json)의 기존 기준을 완화하거나 실패를
  새 기준으로 소급해 통과로 바꾸지 않는다. 재학습·분할 변경도 포함하지 않는다.
- #205의 보수·필수 재실행·실패 인계가 완료돼도 수치 기준 위반이 남아 있으면
  종합 검증 결과와 종료코드는 실패를 유지한다. 다른 티켓이나 부모를 자동 종료하지 않는다.

## 실행 묶음과 보관

1. 측정 전에 실행 ID, 고정 계약, 관련 코드 스냅샷과 hash, checkpoint·manifest,
   사례·헤드·설정·설명 프로토콜을 동결한다. 단계별 환경·실행 명령도 기록한다.
   TensorFlow 기준 측정 환경과 채택 torch 환경의 차이를 명시한다.
2. reference·core·diagnostics·RAM·staging 및 원시 배열을 같은 실행 묶음에 연결한다.
   입력 자료와 단계별 출력의 checksum을 기록하고 조립 시 대조한다.
   조립 시점의 계약 hash를 과거 결과에 붙여 출처를 보증하지 않는다.
3. 필수 단계 누락, 식별 불일치, 원시 자료 변조·누락, 다른 실행 결과 혼합을 거부한다.
   오래된 결과 여부는 timestamp만으로 판단하지 않는다.
4. 측정 중단 또는 관련 코드·계약·모델·설정 변경 시 새 실행 묶음에서 필수 측정을
   처음부터 수행한다. 단계별 측정 재개 기능은 추가하지 않는다. 동일한 완료 묶음의
   요약 재조립은 허용하며 입력 checksum을 다시 검증한다.
5. 수치 기준을 위반해도 유효한 실패 결과가 기록됐다면 나머지 필수 단계를 계속
   수집한다. 실행 중단·자료 누락과 수치 실패를 구별한다. 최종 결과는 둘 다
   실패로 처리하며 실행 완료를 수치 통과로 표현하지 않는다.
6. 계약·관련 코드·manifest·원시 결과를 아래 두 위치에 보관하고 사본 간 checksum을
   확인한다. 모델 bytes는 기존 checksum 고정 보관소와 연결한다.

   - `C:/project-backups/dashboard-v3/issue205/<run_id>/`
   - `D:/MC_project-backups/dashboard-v3/issue205/<run_id>/`

   Git에는 실행 manifest·checksum·명령·종합 결과·인계를 기록한다. 로컬 볼륨
   두 곳의 사본을 외부 또는 물리적으로 독립된 백업이라고 주장하지 않는다.

## 검증 도구 보수

- **필수 검사 목록과 종합 판정:** 동결 계약에서 기대하는 모델·사례·헤드·입력·
  점·설정·층·버전·필수 출력의 검사 목록을 구성하고 실제 결과와 대조한다.
  core/diagnostic의 실패 수뿐 아니라 모든 필수 claim과 staging 결과를 반영한다.
  필수 실패·누락·식별 불일치는 비정상 종료코드로 반환한다.
- **층별 parity:** 모든 층에 scaled 절대오차와 상대오차 기준을 각각 적용한다.
  실제·기준 측정의 층 집합 누락도 검출한다. 요약의 최악 층 선택은 판정과 분리한다.
- **버전:** 계약의 Python·Keras·torch·NumPy·SHAP·h5py 6개를 모두 검사한다.
  보고되지 않은 키를 건너뛰지 않는다.
- **유한값:** seed 0/1/2·반복·정밀 실행의 모든 필수 전방 출력·gradient·IG·SHAP·
  기준값·완결성/가법성 항·진단값을 확인한다. 비유한값이 비교 연산의 부작용이나
  요약 과정에서 누락되지 않도록 한다.
- **판정 수치:** 코드에 별도 숫자가 남아 있다면 동결 계약과의 일치를 확인한다.
  실패를 없애기 위한 변경은 하지 않는다.
- **재생성 명령:** 각 도구에 필요한 출력 위치를 명시하고, 빈 결과 디렉터리에서
  reference부터 종합 report까지 문서의 명령만으로 생성한다. 실패 결과가 있어도
  전체 근거를 수집하는 실행 순서와 예상 종료코드를 설명한다.

## SHAP 동시성 및 캐시

- NumPy 전역 RNG 저장·seed 설정·표본추출·복원 전체를 공유 잠금으로 보호한다.
  같은 잠금에 참여하는 SHAP 호출 사이의 재현성을 보장하며 다른 전역 RNG
  소비자까지 보호한다고 주장하지 않는다. #194의 직렬 worker와 공용 함수의
  동시성 보장을 구별한다.
- 정상 완료와 seed 이후 계산 구간 내부의 일반 예외·협력적 취소에서 RNG 복원을
  확인한다. 생성자 단계에서만 취소되는 테스트로 대체하지 않는다.
- 같은 입력·seed·64/4의 실제 KernelSHAP 동시 호출과 직렬 호출을 비교한다.
  합성 함수 테스트와 실제 두 모델의 관련 재실행을 구별한다.
- checkpoint·계열·헤드·서열·설정·seed·설명 프로토콜의 동일성을 확인하는
  캐시 경계를 둔다. 출처 없는 구 사전계산 NPZ는 거부하고 새 계산으로 처리한다.
  메모리/디스크 캐시의 재사용 경계를 각각 확인한다.
- 새 포맷의 cache hit와 fresh 계산 일치, 식별 항목이 다른 결과 거부를 검증한다.
  기존 NT 4개 파일을 무조건 64/4로 다시 생성하지 않는다. 실제 NT 캐시 품질 승인과
  단위 교정 후 프로토콜 확정·재생성은 #201에 인계한다.

## 설치 명세와 독립 복구

- 빌드 설치 명세에 Keras 3.14.1·h5py 3.14.0 등을 반영하고 필수 전이 의존성을
  식별한다. 설치된 개발 PC 패키지를 선언된 의존성 대신 취급하지 않는다.
- 준비된 코드·모델·manifest·최소 실행 의존성을 독립 위치로 복구한다.
  복구 위치의 자산 checksum을 확인하고 원본 repo·모델 경로 접근이 거부되는
  조건에서 두 모델의 최소 전방·gradient 실행을 수행한다.
- 기존 Python 실행 파일·표준 라이브러리·OS DLL은 명시적 외부 전제로 허용한다.
  실제 사용한 실행 파일·버전·경로·모듈 출처와 환경을 기록한다.
- 네트워크 차단 방법과 확인한 범위를 기록한다. 프로세스 내부 차단을 OS 수준
  차단으로 표현하지 않는다. TensorFlow가 import되지 않는 target 최소 실행과
  TensorFlow 기준 측정 과정을 구분한다.
- 새 Python 환경의 오프라인 설치, 최종 배포본 빌드, 깨끗한 Windows·OS 수준
  네트워크 차단 검증은 #204 범위로 유지한다.

## gradient 진단과 정밀 설정

Q10~Q13에서 #205의 추가 후보 비교, 차분 진단 대상과 유한한 실험 규모를 승인했다.
후보 선정·판정 규칙 및 고정밀 진단의 간격·시간 한도는 Q14~Q16 답변 대기 중이다.

- 기존 Cas12a 상대 L2 2% 기준과 원래 실패를 보존한다. 실패한 사례·입력·점·
  방향에 맞춘 차분 간격 sweep과 활성함수 경계 교차 진단을 측정 전에 등록한다.
  기존 x의 좌표 진단을 alpha=0.5의 방향 실패 원인으로 대신 사용하지 않는다.
- 기존 실패와 보수 후 새 실패의 합집합에서 동일한 입력·점·좌표/방향을 보존하고,
  `h={3e-2,1e-2,3e-3,1e-3,3e-4,1e-4}`을 비교한다. 좌표 검사는 해당 입력의
  전체 gradient를, 방향 검사는 기존 seed 193의 32개 방향을 비교한다.
  모델별 통과 대조군 하나도 사전 지정하며 전체 보간 경로 탐색으로 넓히지 않는다.
- 두 autograd의 일치, IG 적분 오차 개선, 차분 검사의 성공 여부를 별도로 기록한다.
  원인을 입증하지 못한 사례는 미해결로 남길 수 있다.
- 검사법 변경이 필요하다는 근거가 확보되면 별도 버전의 새 계약을 사전 등록해
  새 실행에 적용한다. 기존 실패를 덮어쓰지 않는다.
- IG 256과 큰 SHAP 설정은 정밀 재시도 후보로 검증한다. SHAP의 배경 선택과
  부분집합 표본추출 변동을 분리해 측정한다. seed 재현성이나 가법성만으로
  안정성 통과를 주장하지 않는다.
- #205의 추가 후보 비교는 고정 8사례·현 SpCas9 선택 헤드·현 Cas12a 경로에
  한정한다. 오차·변동·비용을 인계하고 사용자 정밀 재시도 설정의 최종 품질
  승인은 요구 헤드와 채택 경로를 다루는 #199/#200에 남긴다. NT는 #201이다.
- IG는 32/64/128/256단계를 각 1회 비교한다. SHAP은 배경 4·배경 seed 0에서
  샘플 64/128/256/512와 부분집합 seed 0/1/2, 샘플 512·부분집합 seed 0에서
  배경 4/8/16/32와 배경 seed 0/1/2를 비교한다. 동일 난수열의 prefix를 사용한다.
  교집합 한 개를 재사용한 1차 비교는 전체 184회이며 모델별 후보 최대 하나의
  독립 seed 3×3 확인과 동일 seed fresh 재호출을 포함해 SHAP 최대 240회로 둔다.
- 추가 후보 비교 예산은 총 90분이다. 호출 사이에서 예산을 확인하며 소진 후
  추가 호출을 시작하지 않고 미시작·미검증을 기록한다. 기존 필수 재검증·차분
  진단·RAM·독립 복구는 이 예산과 별도로 수행한다. 최종 후보 선택·판정은
  인터뷰 Q14·Q15에서 확정할 때까지 미정이다.
- float32 진단 후 미해결 위치에만 조건부 float64 진단을 한 차례 허용한다.
  dtype 외 구조·헤드·가중치 값을 대조한 별도 사본이 적격성 검사를 통과할 때만
  사용한다. 적격성 확인 불가·연산 미지원이면 진단 불가로 종료하고 수동 LSTM이나
  backward 재구현으로 확대하지 않는다. 간격·지표·시간 한도는 Q16에서 확정한다.
- non-NT의 선택한 예측 행 한 건에 약 1분 대기를 허용할 수 있는 후보를 검토한다.
  예상 비용·진행률·취소 제공을 #199/#200에 인계한다. 1분은 설계 목표이며
  모든 입력의 시간 보장이나 강제 timeout 설정이 아니다. NT 예산은 별도 측정 후
  #201에서 다룬다.
- [탐색 성능 결과](../runtime/issue205-performance.md)의 Cas12a 약 40초는
  모델 적재 후 한 사례·헤드에서 SHAP 512/32를 새로 계산한 시간이다.
  샘플만 512로 늘린 512/4는 약 4.7초였다. UI 전체 지연·NT 시간·수치 품질
  통과로 일반화하지 않는다. 계산량 증가가 유일한 개선책이라는 결론도 내리지 않는다.

## 구현 및 검증 순서

1. 기존 자료를 보존하고 관련 코드·설치 명세·캐시·검증 도구를 보수한다.
2. 관련 회귀 검증을 추가하고 아래 경계부터 확인한다. 새 harness 테스트 파일의
   이름과 진단 명세의 세부 수치는 구현 시 정하되 측정 전에 기록한다.
3. 추가 진단 계약과 실행 manifest를 고정한다. 기준을 확인한 뒤 결과를 측정한다.
4. 빈 디렉터리에서 reference → core → diagnostics → RAM → 독립 staging →
   종합 report를 생성한다. 필수 단계의 판정과 실제 종료코드를 모두 기록한다.
5. 원시 자료와 고정 스냅샷을 Q9의 두 보관 위치에 복사·검증하고 Git 요약과 연결한다.
6. 문서·분모·헤드·RAM·원인·정밀 설정의 표현을 정정하고 후속 티켓에 인계한다.

필수 회귀 범위:

- 오프라인 실패, 필수 검사 누락, 식별 불일치가 전체 실패·비정상 종료로 이어짐.
- 절대오차 최댓값이 아닌 다른 층의 상대/scaled 위반도 검출함.
- 버전 누락 및 seed 1/2·반복·정밀 실행 등의 NaN/inf를 검출함.
- SHAP 동시·직렬 재현성과 정상·예외·취소 후 RNG 복원.
- 구 캐시 거부, 새 캐시 동일성 확인과 fresh 계산 일치.
- 원본 경로 없이 복구·최소 실행, 빈 디렉터리에서 전체 명령 재생성.
- 두 실제 모델의 관련 parity·함수 일치·gradient·IG·SHAP 재실행.

기존 `test/test_non_nt_runtime.py`, `test/test_explain.py`,
`test/test_explain_cache.py`, `tests/test_shap_cache.py`, `tests/test_worker_cache.py`
등에서 변경과 관련된 케이스를 먼저 선택한다. 새 검증 도구의 직접 회귀도 추가한다.
[AGENTS.md](../../AGENTS.md)에 따라 실행 전에 선택 이유를 설명하고 결과에는
실제 명령, 통과·실패·건너뜀 수와 미검증 항목을 기록한다. 전체 저장소 테스트는
기본 실행하지 않는다. 실제 모델·복구 등 티켓 필수 검증은 생략하지 않는다.

## 현재 산출물과 검증 상태

설계 인터뷰, 용어집, 근거 보존 ADR, 탐색 성능 기록과 원시 자료를 작성했다.
문서 5개, 상대 링크 12개, 참조 테스트 경로 5개, 원시 파일 checksum 9개를
확인했고 모두 통과했다. `git diff --check`도 종료코드 0이었다. 제품 결함 보수 코드와
새 수치 품질 검증 묶음은 아직 없다. 탐색 성능 호출 52회 완료를 #205의
수용 검증 통과로 계산하지 않는다.
