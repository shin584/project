Part of #191. #193 구현에 대한 독립 검토에서 확인한 결함을 보수하고, 검증 결과와 후속 작업 인계를 정정한다.

## 문제와 변경 후 동작

현재 검증에는 필수 실패가 전체 판정에서 빠지거나 검사 대상 일부가 누락되는 경로가 있다. 문서에 적힌 명령만으로 결과 파일을 재생성할 수 없고, 오프라인 staging은 원본 워크트리에도 의존한다. SHAP seed 수정은 직렬 호출을 재현하지만 동시 호출에서는 전역 RNG가 충돌한다.

수정 후에는 등록된 모든 필수 검사와 오프라인 결과가 일관된 종합 판정에 반영돼야 한다. 원본 작업 폴더 없이 복구한 입력으로 최소 실행을 재현하고, 검증 범위·실패 분모·후속 담당 티켓을 정확히 인계한다.

## 확인한 구현 및 검증 결함

### 1. 빌드 의존성 선언 누락

- [`packaging/desktop.spec`](https://github.com/shin584/project/blob/c7df95b22683fbcefc0e560266bff01ef6190dc2/packaging/desktop.spec)는 Keras를 수집하지만 [`packaging/requirements.txt`](https://github.com/shin584/project/blob/c7df95b22683fbcefc0e560266bff01ef6190dc2/packaging/requirements.txt)에는 `keras==3.14.1`, `h5py==3.14.0`가 없다.
- 개인 PC의 설치 상태가 새 빌드 환경의 의존성을 대신하고 있다.
- 동결한 버전을 설치 명세와 오프라인 설치 자료에 반영하고 필요한 전이 의존성도 식별한다. 실제 배포본 빌드와 깨끗한 Windows 검증은 #204와 구분한다.

### 2. 오프라인 실패가 종합 판정과 종료코드에서 누락

- [`assemble_verification.py:100`](https://github.com/shin584/project/blob/c7df95b22683fbcefc0e560266bff01ef6190dc2/docs/runtime/assemble_verification.py#L100)의 `overall`은 core/diagnostic 실패 수만 확인한다. 함수는 전체 실패 상태에서도 종료코드 0을 반환한다.
- 격리된 임시 입력으로 core/diagnostic을 통과시키고 staging을 실패시키면 `open_failures`에 오프라인 실패가 있는데도 `overall=pass`, 종료코드 0이 재현됐다.
- 모든 필수 claim에서 종합 상태를 계산하고 필수 실패에는 비정상 종료코드를 반환한다. 필수 검사 누락도 통과로 취급하지 않는다.

### 3. SHAP seed 처리의 동시성 결함

- [`xai/explain.py:148`](https://github.com/shin584/project/blob/c7df95b22683fbcefc0e560266bff01ef6190dc2/xai/explain.py#L148)의 `get_state → seed → shap_values → set_state`가 잠금 없이 프로세스 전역 NumPy RNG를 공유한다.
- `ExplainCache`는 동시 미적중 계산을 허용한다. 실제 KernelSHAP의 동일 입력·seed·64/4 호출 두 개를 seed 직후 Barrier로 겹치게 하자 `max |a-b| = 4.9986489e-05`, 직렬 결과와의 차이는 최대 `5.7984822e-05`로 동일값 검사가 실패했다.
- RNG 저장부터 복원까지 전체 구간을 공유 잠금으로 직렬화하거나 프로세스로 격리한다. 공유 잠금만 적용할 경우 이 잠금을 사용하지 않는 다른 전역 RNG 소비자까지 보호한다고 주장하지 않는다.
- #194의 직렬 worker가 해당 데스크톱 경로를 보호할 수 있다는 사실과 공용 함수의 보장은 구분한다. 정상·예외·취소 후 RNG 상태 복원도 확인한다.

### 4. 독립 오프라인 복구 증거 부족

- [`stage_offline.py:49`](https://github.com/shin584/project/blob/c7df95b22683fbcefc0e560266bff01ef6190dc2/docs/runtime/stage_offline.py#L49)은 의존성을 복사한 staging과 함께 원본 repo를 `sys.path`에 넣고, 소스·모델은 원래 워크트리에서 읽는다.
- #193의 요구사항은 모델·manifest·도구/의존성을 로컬 staging하여 네트워크 없는 준비·복구와 최소 실행을 확인하는 것이다. 현재 증거는 TF-free 의존성 부분집합의 실행에 한정된다.
- 고정된 코드·모델·manifest·필요 의존성을 독립 위치로 복구하고 원본 경로를 사용할 수 없는 조건에서 최소 실행한다. 네트워크 차단 방식과 사용한 Python 실행 파일/표준 라이브러리 등 외부 전제도 기록한다.
- OS 수준 네트워크 차단과 깨끗한 Windows PC의 최종 배포 게이트는 #204에 남기되, 이 이슈의 staging 결과와 혼동하지 않는다.

### 5. 문서의 결과 재생성 명령 불완전

- [`stage_offline.py:183`](https://github.com/shin584/project/blob/c7df95b22683fbcefc0e560266bff01ef6190dc2/docs/runtime/stage_offline.py#L183)은 JSON을 출력만 한다. 이후 `assemble_verification.py`는 `.packaging/issue193/staged.json`을 읽지만 문서의 명령에는 파일 저장 단계가 없다.
- 명시적 출력 경로를 제공하고 문서의 전체 명령을 빈 결과 디렉터리에서 재실행한다.
- core/reference/diagnostics/staging의 계약·코드·모델 식별 정보를 연결하고, 누락·오래된 결과·서로 다른 실행의 혼합을 거부한다. 현재 계약 hash를 새로 붙이는 것만으로 과거 측정의 출처를 보증하지 않는다.

### 6. 층별 parity 판정 누락

- [`verify_contract.py:431`](https://github.com/shin584/project/blob/c7df95b22683fbcefc0e560266bff01ef6190dc2/docs/runtime/verify_contract.py#L431)은 사례마다 절대오차가 가장 큰 층 하나를 선택한 뒤, 선택한 층들에만 절대 scaled/상대 기준을 적용한다. 다른 층의 상대오차 또는 scaled 기준 위반을 놓칠 수 있다.
- 모든 층을 두 기준으로 각각 판정하고 요약의 최악값과 전체 판정을 분리한다.
- 현재 저장된 원시 층별 측정값을 전수 재확인한 결과 실제 기준 위반은 0건이었다. 이번 발견은 현재 parity 실패의 증거가 아니라 잘못된 통과 판정이 가능한 검증 결함이다.

### 7. 버전·유한값 검사 범위 부족

- `runtime_versions()`가 Python·SHAP·h5py를 반환하지 않고 검증 루프가 없는 키를 건너뛴다. 계약에는 6개 버전이 있지만 실제 report에는 Keras/torch/NumPy 검사 3개만 있다.
- SHAP 유한값 검사는 seed 0에 한정된다. 계약의 전체 실행 범위에 맞춰 seed 1/2, 반복, 정밀 실행과 모든 필수 출력/gradient/attribution/진단값을 확인한다.
- 등록된 항목이 빠지면 실패시키고 판정에 사용하는 수치 기준이 동결 계약과 일치하도록 한다.

## 결과와 인계 문서에서 정정할 내용

1. **IG 실패 분모:** 기본 32단계는 8사례 중 5개 실패, 256단계는 별도 8사례 모두 통과했다. 두 설정을 합친 `5/16`을 기본 설정의 실패 비율처럼 쓰지 않는다.
2. **헤드 범위:** 전방 parity는 SpCas9 9개 헤드를 비교했지만 IG/gradient 검증은 `Output_SpCas9_NG` 한 헤드다. 나머지 헤드의 XAI까지 검증 완료로 확대하지 않는다. #199에서 요구하는 헤드 검증으로 인계한다.
3. **차분 실패 원인:** 두 autograd의 일치는 강한 근거지만 모든 차분 실패가 ReLU kink 때문이라고 확정하지 않는다. 기존 kink 검사는 원 입력의 ±1e-2, directional 검사는 alpha=0.5에서 h=1e-3로 조건이 다르다. 추가 진단의 사례·step sweep·허용 오차를 먼저 기록하고 실패 위치별로 원인을 확인한다. 기존 실패 기록은 보존한다.
4. **RAM 범위:** 341 MB는 staging의 전방/gradient 최소 실행이며 전체 IG/SHAP 및 UI 트리 피크가 아니다. 루프가 `runtime` 변수를 덮어쓰므로 두 모델을 계속 동시에 보유한다는 보장도 없다. 실제 보유 상태와 측정 단계를 명시하고 전체 트리 비교는 #203/#204에 인계한다.
5. **경고 기능 담당:** 담당 티켓이 없다는 설명을 정정한다. #199는 non-NT SpCas9, #200은 non-NT Cas12a, #201은 NT의 경고·진단·재시도를 이미 포함한다.
6. **정밀 설정의 지위:** IG 256 통과는 현재 고정 사례와 선택 헤드/경로에 대한 결과다. SHAP 512/32는 안정성이 입증된 설정이 아니라 비교 실행이다. 둘을 사용자 기본값으로 자동 채택하지 않는다.

## SHAP 캐시와 후속 작업 인계

- seed 수정 전 생성한 NT `data/precomputed_shap/*.npz` 4개를 새 계산 프로토콜과 동일한 결과로 재사용하지 않는다. checkpoint·모델 계열·헤드·서열·설정·seed·설명 프로토콜의 동일성을 확인하고 구 프로토콜 캐시를 거부하는 경계를 마련한다. NT 단위 교정에 따른 프로토콜 갱신은 #201과 연결한다.
- 기존 캐시를 무조건 64/4로 다시 만드는 것을 해결책으로 삼지 않는다. 설정/프로토콜 확정 후 재생성하고 cache hit와 fresh 계산의 일치를 검증한다.
- 이번 non-NT 측정만으로 기존 NT 캐시의 수치 안정성까지 판정하지 않는다. NT 품질 검증은 #201 범위다.
- #195: Cas12a IG 경로별 계약과 검증을 확정한다. 현재 이중 입력 경로의 수치를 합성 경로의 검증으로 대신하지 않는다.
- #199/#200/#201: 초기 32/64/4를 유지하면서 실패한 설명을 정상 그래프 대신 경고·진단·재시도로 표시하고 예측 표를 유지한다. 경고 동작 성공과 설명 수치 검증 성공은 별도로 보고한다.
- 더 정밀한 재시도를 제공하려면 계산량을 안내하고 그 설정의 품질을 별도 검증한다. SHAP은 배경 선택과 부분집합 표본추출의 변동을 분리해 측정하며 seed 고정/가법성만으로 안정성 통과를 주장하지 않는다.
- 병행 구현은 티켓별 브랜치·워크트리에서 진행하고 통합 기준 커밋을 고정한다.
